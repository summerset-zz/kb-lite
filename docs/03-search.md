# 03 · 检索与打分

**没有向量，没有 BM25，没有分词器。** 只有一层「关键词 × 字段位置」的加权计数，规则短到可以在 `--explain` 里一行一行打给人看。

实现位置：`internal/core/search.go`。

## 与线上版的三处差异

这套规则源自线上知识库（`searchRank.ts`），本地版必须改三处，**其余照抄**：

1. **`leaf` 的来源**：线上取路径末段（`…/array/map`），那是规范标题；本地文件名是 `Untitled.md`、一堆 `README.md`，拿它当「这页就是讲这个的」会系统性误导。改为对**条目标题**匹配。
2. **全文单独一档**：线上只有「摘要」这一档弱命中；本地正文可以全文参与，但权重必须最低（`1`），否则「什么都提过一点」的长笔记会靠堆弱命中顶掉正主。
3. **不需要「分档捞候选」**：线上因为 MongoDB 的 `find().limit()` 不排序，必须按 4 档逐步捞以免真正的候选进不了窗口。本地是全表扫，**直接给所有条目打分再排序**，召回严格更优。

## 关键词拆分

```ts
tokenizeQuery(query: string): Keyword[]
```

1. `query.trim()`，空 → 空数组。
2. 按 **空白与 `.`** 切分（`Element.scrollTo` → `Element` + `scrollTo`）。
3. 去首尾空白；丢掉**不含任何字母或数字**的碎片（`()`、`--`、`&`）。
4. 大小写不敏感去重（保留首次出现的写法）。
5. 最多 **5** 个关键词（超出的丢弃，不要合并）。

每个关键词再生成**匹配器**：

```ts
buildMatcher(kw: string): RegExp
```

- `kw` 是纯 ASCII 标识符（`/^[A-Za-z0-9_$]+$/`）→ **卡词边界**：
  `(?<![A-Za-z0-9_$])${escape(kw)}(?![A-Za-z0-9_$])`，`i` 标志。
  理由：搜 `Array` 不该命中 `TypedArray`，搜 `map` 不该命中 `flatMap`。
- 含中文或其他字符 → **纯子串**匹配，`i` 标志。中文没有词边界，卡了等于搜不到（「数组」应该命中「类型化数组」）。

> **实现注记（Go）**：RE2 没有 lookbehind，所以上面那个词边界**不用正则写** —— 找出每次出现的位置，检查前后 rune 是否属于 `[A-Za-z0-9_$]`。语义与上面的正则完全等价（等价性由排序快照锁住），且更快。**不要把它「简化」成 `\b`**：`\b` 在 `$` / `_` 上的行为与这里不同。

### CJK bigram 辅助

含 CJK 的关键词（长度 ≥ 3 且**整词不带空格**时）额外生成 bigram 变体：`「知识库」→ 知识, 识库`。

- bigram 只参与**加分**，权重为该关键词最终得分的 **×0.5**（向下取整）；
- bigram **不参与** `strong`（结构性命中）判定，只计入「轻命中」；
- bigram 的字面 `keyword` 在 `--explain` 里显示为 `知识(≈)` 以便区分。

理由：`[\s.]+` 切分下「知识库怎么用」是一个关键词，只能靠子串碰运气。中文用户不会按空格写查询，而引入分词器（nodejieba 之类）会带来原生依赖 —— bigram 是零依赖且可解释的折中。

## 参与匹配的字段

| 字段 | 记号 | 说明 |
|---|---|---|
| 条目 `title` | `title` | 标题取值链的结果 |
| `tags[]` | `body` | 与摘要同类（都是「这一篇附带的信息」） |
| `summary` | `body` | 同上 |
| `tocText` | `toc` | 所有章节标题 + 面包屑 |
| `relPath` | `path` | 相对路径（含目录名） |
| 条目标题（= `title`）当叶子 | `leaf` | 见差异 1 |
| `body`（全文） | `full` | 最弱一档 |
| 关键词本身是识别符时额外的路径末段 | `leaf` | 见下 |

一致性要求：所有字段**先 `toLowerCase()`** 再匹配（匹配器本身带 `i`，但预先小写避免 locale 差异带来的抖动）。

## 打分

对每个关键词算一个 `Hit`：

```ts
type Hit = { keyword: string; title: boolean; path: boolean; toc: boolean; leafPart: boolean; body: boolean; full: boolean };
```

```ts
strong   = 命中 (title || path || leafPart) 的关键词数
weak     = 命中 (body) 且 !(title || path || leafPart) 的关键词数
fullOnly = 只命中 full 的关键词数
inTitle  = 命中 title 的关键词数
inPath   = 命中 path 的关键词数
inToc    = 命中 toc 的关键词数
inLeaf   = 命中 leafPart 的关键词数
```

```
score = strong  * 10
      + inTitle * 5
      + inToc   * 4
      + inLeaf  * 4
      + inPath  * 3
      + weak    * 3
      + fullOnly* 1
      + Σ(bigram 加分, 见上)
```

**权重必须维持这个序**：

```
只命中全文 < 只命中摘要/标签 ≲ 命中路径 ≲ 命中章节标题 ≈ 命中标题 ≈ 命中条目标题 < 命中标题且命中路径
```

调权重时只允许在这个序内微调，并且必须跑 `go test ./internal/core -run Rank` 里的排序快照。

### 排序

```
1. score 降序
2. title 字典序升序（localeCompare，稳定输出）
3. relPath 升序
```

## 多查询合并

一次调用的 `q` 可以有多个（`?q=a&q=b`，最多 5 个）。**每个查询独立完整算分**，然后按 `rel_path` 合并、**分数相加**、重新排序。

> 不把多个查询的词混在一起算：`Array map` 这种「所有词都在标题里」的强信号，混词之后几乎永远不成立。这个坑线上踩过。

合并的语义：「被越多查询命中、命中位置越结构化，越靠前」。只传一个查询时，结果与单查询完全一致。

## 候选窗口

```
perQuery = min(max(limit * 4, 10), 100)
```

先按 `perQuery` 给每个查询取前 N，再合并、重排、截到 `limit`。这样「A 查询的第 6 名」也有机会进入合并池。

## `--explain` 输出（CLI 与 UI 共用）

```
我的笔记 ← "部署 回滚"
关键词 = ["部署","回滚"]   返回 3 条

  1.  42  运维手册                       ops/runbook.md
         部署: 标题 路径 章节 全文      回滚: 路径 分支 章节
  2.  21  服务器迁移记录                  ops/migrate.md
         部署: 全文                     回滚: 全文
```

命中位置的名称固定为：`标题 / 条目标题 / 路径 / 章节 / 摘要 / 全文`（`body` 在界面上叫「摘要」或「标签」，按来源不同显示）。

**这条输出是产品的一部分**，不是调试残留：用户会自己加内容、自己调 skill，出问题时唯一能自助的入口就是它。

## 性能与上限

- 全表扫：`entries × keywords` 次正则测试。5000 篇 × 5 关键词 ≈ 25k 次 `/x/` 测试，实测 **< 20 ms**。
- 超过 **50000** 篇时降级为 `--fast` 模式：先用 `search_text` 的 `includes()` 粗筛（单次字符串包含，比正则快一个量级），只对命中的条目精算。
- 正则**不带 `g` 标志**（无状态，可复用），且**只允许来自 `buildMatcher()`** —— 用户输入永远经过 `escapeRegExp`。

## 刻意不做

写在这里防止实现者顺手加：

- ❌ 同义词表 / 停用词表（中文停用词会误伤「的」「在」出现在标题里的条目，且不可解释）
- ❌ 拼音匹配（引入词典，收益不确定）
- ❌ 词干化（英文场景已被「标识符卡词边界 + 子串」覆盖）
- ❌ TF-IDF / 长度归一化（笔记长短差异巨大，归一化会让长文永远排不上；我们靠「结构性命中」而不是频次区分）
- ❌ 模糊匹配（拼写纠错）。搜不到就是搜不到，让 agent 换词比猜更可靠。
